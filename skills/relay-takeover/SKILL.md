# Relay Takeover

用户会传入一条 ticket 的路径或编号。这条 ticket 应该处于 `Status: needs-strong`，由 `/relay-tickets` 标注过。relay 的规则和 ticket 模板见仓库里的 `docs/agents/relay.md`。

## 流程

### 1. 读状态，不重读全部

- 读 ticket 正文（重点是 `## 执行步骤` 的勾选状态），以及 `## Comments` 下最新一条交接记录。
- 读 executor 开工以来的 `git log` 和 `git diff`，只看和这条 ticket 相关的部分。

交接记录加 diff 就够你接手了。不要从头通读整个项目：省下这部分 token 正是接力开发的意义。

### 2. 检查越界、跳步和绕开

对照 diff 和步骤勾选状态检查三件事：

- **越界**：弱模型忘了停，直接写了 strong 步骤或碰了触发型 strong zone。当作草稿审查，对就保留，不对就重写。这不算事故，接手本来就要兜住这种情况。
- **跳步**：停下的那一步后面，还有被做过或被勾选的步骤。弱模型应该按顺序停在第一个 strong 步骤前。这些步骤同样当草稿审查；它们依赖的 strong 步骤还没做时，按 strong 步骤做完后的样子改正。
- **绕开**：弱模型没有停，而是在允许修改的文件里另写了等价实现、换了一个接口或做法、把本该停下的一项判成缺陷或不适用后继续往下。找出来，按 strong zone 原本的要求重做，撤掉绕开的那一份。

同时检查已完成的部分有没有偏离 ticket，比如悄悄简化了实现、改了接口、换了做法。发现就一并修正，并记进第 4 步的记录里。

### 3. 处理停下的原因

- **停在 strong 步骤或触发型 strong zone**：按 ticket 和相关 ADR 里的既定决策实现它，尽可能用 `/tdd`。实现完勾选这一步。只做这一步，以及紧跟在它后面、连续的 `[strong]` 步骤；后面的 `[weak]` 步骤留给弱模型，不要顺手做掉。用户明确说接下来由强模型一路做完时除外。
- **停在执行规则第 5、6 条（兜底情况）**：先判断是执行问题还是计划问题。
    - 执行问题：直接修。
    - 计划问题：修改本 ticket 的执行步骤（例如补上漏写的前置 `[strong]` 步骤）。如果影响到后续 tickets，一并修改，并告诉用户改了哪几条。如果这个新决定满足 ADR 的三个条件（见 `/domain-modeling`），提议记一条 ADR。

### 4. 交还

- 运行这条 ticket 相关的测试，确认通过。
- 提交。
- 把 `Status:` 改回 `ready-for-agent`；如果整条 ticket 已经完成，按 tracker 的约定标记完成。
- 在 `## Comments` 下追加一条记录：做了哪几步、修正了哪些越界、跳步或绕开，以及「executor 从第 N 步继续」。
- 告诉用户可以切回 executor 了。
